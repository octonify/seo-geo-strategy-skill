**Now.** Three steps where there were two:

|---|---|---|
| 5 | Classify intent — Pass A, from the query | the candidate list from step 3, and nothing else |
| 6 | Read the SERPs | the candidate list from step 3, the locality and dataset from step 1 |
| 7 | Classify intent — Pass B, from the observed SERP | the SERP read blocks from step 6, the Pass A column from step 5 |

Steps renumbered 1–13. Integers rather than D52's `5a`/`5b` shorthand, for the reason in D55: the new contract rule is stated in terms of *later*, and it needs a procedure whose numbering and whose execution order are the same sequence.

### F3 — partial SERP observation was undefined on both sides of the handoff

**Was.** The read protocol handled a read missing its date, locality or surface. Nothing handled a read missing *positions*. `Done when` items 7 and 8 in research and item 5 in architecture knew only observed and not-observed, and the overlap rule's third row read "either SERP not observed". A SERP with 4 of 10 positions captured was neither, and the first run had to improvise at exactly the point the policy kernel says to stop and report.

**Now, on the research side.** `serp-read-protocol.md` §2 opens with three observation states — `observed`, `partial`, `not observed` — with what each means and how each is recorded. `partial` carries its captured position count, marks every field the read could not reach `Unknown — not captured`, and is explicitly neither a degraded `observed` nor a soft `not observed`. The captured count is recorded because the architect's overlap test needs it and cannot apply a floor to a count the pack did not carry. Observation state is now a labelled field of every read. Continue-silently gate 9 governs the condition, so it is no longer a condition on neither list.

**Now, on the architecture side.** `cannibalization-guardrails.md` §2.1 sets the position floor at **8 of the top ten**, and §2's verdict table gains the row. The reasoning is D56 and the operative part is the asymmetry:

| Situation | Verdict |
|---|---|
| Either read below 8 of 10 captured | `Unknown` — one page for now |
| Shared count ≥ 4, reads at or above the floor | One page — unseen positions can only raise a count already over the threshold |
| Shared count ≤ 3 and either read short of a full ten | `Unknown` — the unseen positions could carry it over |

A partial read can send a pair to one page and can never send it to two. Same direction as an unobserved SERP, same reason.

**`Done when` items, all three now admitting the third state.** Research item 7 requires every candidate to be in exactly one of the three states with the pack saying which; item 8 states what a `partial` block must contain, which is the same four fields as an `observed` one with the unreachable fields marked. Architecture item 5 requires both routes to `Unknown` to be named separately — an unobserved SERP and a partial one below the floor are different facts.

Templates updated so the items are checkable against a real deliverable: the pack template's SERP block gained a `State:` line and a partial-candidates list; the cluster record template's membership table carries captured position counts and states the floor beside the threshold.

**How a future run behaves differently.** The run that produced the first report carried two partial reads, recorded them as partial, and treated the affected overlap pair conservatively — correctly, but by improvisation, and it said so. The same run now follows a rule: the reads are `partial` with their counts, continue-silently gate 9 covers them without a stop, and the overlap pair's verdict follows from the floor rather than from judgement. Its record shows the counts, so a reader can see how close each call was.

### F5 — an enforced count with no definition

**Was.** Both Skills required the evidence-basis totals to equal the count of labelled values. Nothing said what one labelled value is. The first run defined a rule, scripted it, and stated it beside its counts — honest, and also proof that a second operator would define a different one and both would report `Pass`.

**Now.** `references/skill-contract.md` §5 defines it once, for all three Skills: one labelled value is one occurrence of one of the five label words at a position where it labels a value, with an inclusion list of three positions and an exclusion list of five. The three edge cases where two honest operators would otherwise diverge are named explicitly — a row with a label cell and two labelled value cells counts three; an empty label cell counts nothing and is a defect in the row; `Unknown` counts like the other four.

`metric-label-map.md` §4 and `observation-label-map.md` §4 now point at it, and all three Skills' assembly steps say the rule is the contract's and the run does not define its own.

**How a future run behaves differently.** It does not write a counting rule into its handoff summary. It applies the contract's and reports five numbers a second operator can reproduce by searching the file.

### F6 — a `Done when` item made one of its own gate's options unreachable

**Was.** `content-strategy-architect` item 1: "If any required key reads `missing`, Status is `stopped`." `planning_record.row_identifier_field` is required. Gate 2 option 3 produces the record and the briefs with the write `stopped` and the run `partial`. Under the literal reading, option 3 does not exist.

**Now.** Item 1 is scoped: `stopped` follows from a missing required key **except one whose absence has its own stop-and-ask gate, which that gate governs**. The one key that qualifies today is named, along with what gate 2 option 3 produces, and the item says what goes wrong without the scope.

**Extended to `local-presence-manager`, and reported rather than done quietly.** That Skill's item 1 carried the identical contradiction three times over: gate 2 option 3 (observation-only run, `partial`) when `local_presence.canonical_nap` is absent; gate 6 option 2 (proceed with every GBP row `missing — no profile found`); gate 7 option 2 (proceed on the observed state). All three keys are required; under the unscoped item all three options were unreachable. D50's standing rule governs — a follow-up naming files names the ones known to need the change, and a file left asserting something a just-approved decision has made false is a defect, not scope discipline. Recorded as D58.

`seo-geo-research` was left alone: it has no such key. Its gate 1 option 3 stops, which is what its item 2 already says.

**How a future run behaves differently.** The first run resolved this by scoping item 1 itself and writing the interpretation into the record. A future run reads the scope off the item.

### F1 — gate 3 read as being about the channel

**Was.** "`access_mode` is `browser_agent` or `api` but no such access is connected." The first run met a browser that was connected and driving fine, reaching a tool that served its logged-out page. Concluding that an unauthenticated tool equals "access not connected" took inference, and before that inference landed the run spent four of five free checks on the logged-out tool.

**Now.** "…but the named tool cannot actually be read: not connected, not authenticated, or not reachable", followed by the sentence that does the work: *the channel working is not the test*, with the three cases named — a browser that drives fine but reaches a logged-out page, an API returning an auth error, a tool simply unreachable. Option 2 now reads "connect **or authenticate** the access and re-run".

**How a future run behaves differently.** It fires the gate when it sees the logged-out page, before probing the free checker.

### F4 — "existing page" versus "planning row" was ambiguous

**Was.** Step 2's inherited-decisions pass was written for pages already existing. `Done when` item 3 said "one row per page already existing in this cluster", and continue-silently gate 7 said a cluster with no existing page writes `none`. The first run's cluster had no built pages and three planning rows already declaring primary keywords. Treating it as decision-free would have hidden three undocumented decisions.

**Now.** Stated explicitly in three places:

- Step 2 is retitled "Inventory the cluster's inherited decisions and re-verify them" and states that an inherited decision is a declared primary keyword, not a built page — a planning row naming a target is a decision somebody made, with or without a trail, and this Skill is about to decide on top of it.
- `primary-keyword-selection.md` §5 gains a table of the two kinds and the sentence in full: a planning row that declares a primary keyword is an inherited decision even when no page exists. It states why this needs saying — the natural reading of "inherited" is "already built", and that reading makes a green-field cluster look decision-free precisely when its declarations are least likely to carry a trail, because nobody archives research for a page that was never written.
- `Done when` item 3 and continue-silently gate 7 both changed. The table carries a `Kind` column so an audited page and an audited intention are distinguishable without inferring it from the URL cell, and the empty case now reads `none — no existing page and no planning row declaring a primary in this cluster`.

Where a planning row and a built page describe the same target, they are one row, marked as the page.

**How a future run behaves differently.** The first run reached the right answer by judging that planning declarations count, and surfaced three re-verification defects on a green-field cluster. A future run is told to.
